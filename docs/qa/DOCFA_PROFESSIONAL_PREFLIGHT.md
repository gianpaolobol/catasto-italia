# [Codex] Preflight documentale unitario DOCFA — 2026-11-28

Gate #77: il manifest delle evidenze preesistente lega l'archivio provinciale e 36 riscontri, ma non i byte di software, specifiche e modelli. Questo passaggio colma il collegamento documentale senza sostituire l'esecuzione di DOCFA ufficiale.

1. Generare il kit canonico con `node scripts/generate-docfa-comparison-kit.mjs <kit>`; non modificarlo.
2. Acquisire dal portale dell'Agenzia delle Entrate il software, l'archivio provinciale, i tracciati e i modelli effettivamente utilizzati. Conservare tutto fuori dal repo. La pagina corrente è https://www.agenziaentrate.gov.it/portale/software-docfa-4005 (accesso non riuscito nella sessione del 28/11); non sostituire con Docte2 o una versione precedente. Verificare firma/hash pubblicati quando disponibili e annotare il metodo effettivo. Il tool non effettua questa verifica.
3. Per un unico ambiente di prova (stessa provincia/versione per sei scenari), salvare nella cartella riscontri i file opachi `docfa-installer.bin`, `docfa-specifications.bin`, `docfa-models.bin`, `archive-<sha256>.bin`. Non eseguirli dal tool; non modificare i byte. Calcolare SHA-256 dei quattro file con strumenti locali.
4. Creare `docfa-source-declarations.json`, UTF-8, con esattamente questi campi: version = "0.1.0", kind = "local-docfa-source-declarations", docfaVersion (es. formato x.xx.x, versione effettiva), province (due lettere maiuscole), sources (quattro oggetti, uno per role installer, archive, specifications, models). Ogni oggetto contiene solo role, url (HTTPS sul dominio agenziaentrate.gov.it o sottodominio, URL effettivo), acquiredOn (YYYY-MM-DD), sha256 (64 esadecimali minuscoli), verificationMethod (metodo dichiarato, testo non vuoto). Nessun URL viene aperto; non includere segreti o token. Il file non è una certificazione.
5. Nei sei registri DOCFA, usare esattamente la versione e provincia dichiarate, archiveSha256 corrispondente e specificationReference = "sha256:" seguito dall'impronta dei tracciati. Registrare la data reale della prova, non precedente alle acquisizioni, e il riferimento all'esecuzione locale. Completare i 36 riscontri con prove effettive secondo DOCFA_EVIDENCE_INTEGRITY.md. Generare il manifest delle evidenze una sola volta e conservarne una copia indipendente.
6. Eseguire `node scripts/verify-docfa-professional-preflight.mjs <kit> <riscontri>`. Exit 0: completezza documentale senza differenze dichiarate; exit 2: documentazione completa ma differenze da esaminare; exit 1: preflight fallito. Anche exit 0 non attesta vigenza, autenticità, corretta installazione, compatibilità, qualità delle prove o V1.0. Le non applicabilità richiedono revisione umana. Conservare separatamente il report, incluse le impronte di entrambi i manifest; non pubblicare dati o archivi reali.

Il tool è read-only, usa nomi fissi, limiti di lettura, verifica SHA-256 e ricalcolo del kit e dei registri. Non costituisce sandbox contro mutazioni concorrenti; le directory locali devono restare ferme durante il controllo. Non applica regole catastali nuove, non apre file eseguibili e non trasmette nulla. Consente un solo set di fonti per confronto: per province/versioni diverse occorrono esecuzioni separate. La stessa impronta per più ruoli viene rifiutata perché non identifica quattro artefatti distinti; eventuali pacchetti combinati richiedono una futura estensione documentata.

Accettazione: kit canonico, 36 riscontri e manifest intatto, quattro file e metadati coerenti, rifiuto di dominio ingannevole, mutazioni, cronologia incoerente e discordanza provincia/spec. Fixture esclusivamente sintetiche; CI Linux/Windows richiesta. Revisione sequenziale, nessun agente indipendente disponibile. Nessun archivio vigente acquisito, nessun DOCFA eseguito.
